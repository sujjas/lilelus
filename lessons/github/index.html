GitHub: the magic recipe book

By the end, Lizzie can say what a repo, commit, branch and pull request are, and she will have changed the live demo site herself, signed in to her own GitHub account.

10 min idea 45 min build 10 min explain back + journal
The repo ↗ The live site ↗ Her GitHub page ↗ Vercel dashboard ↗

Before class

about 15 min, on your own

Heads-up about preview links. When you open a pull request, Vercel posts a Preview link. New Vercel projects protect previews behind a Vercel login, so it will open on your laptop but not on Lizzie's device. Show it on your screen. To make previews public, go to the Vercel project's Settings → Deployment Protection.

The idea

10 min

Start with something she already knows: mum's recipe book. Now imagine a magic one that remembers every version of every recipe, ever.

Use her GitHub page for this part. Go through The words, in cake language together, then let her play Try it: bake a change. It's a pretend recipe book where nothing can break, and it shows the whole plan below before she does it for real.

Say it like this: “GitHub is a magic recipe book for websites. Every time we save a change, it keeps the old page too, so we can never really lose anything.”

Then add the last piece: Vercel watches the real book. Whenever main changes, Vercel bakes the website again, and the live site updates by itself.

This is today's whole plan in one picture. Show it at the start, then again at the end once she's done it.

The golden rule: this repo is public, so anyone in the world can read it, forever. Never put phone numbers, passwords or secret codes in it. (That's why the demo has no WhatsApp number.)

Quick check before building: “If you break something on a practice branch, does the live site break?” (No. Only main goes live.)

The build

45 min

Each step is one dot in the history. Before every click, Lizzie predicts what will happen. She does the clicking on her own laptop, signed in as herself. You guide and ask the questions.

  1. step 1 · 8 min

    Tour the recipe book

    She clicks
    1. Open the repo.
    2. Scroll slowly to the README at the bottom.
    She checks
    • Finds index.html, style.css and script.js: the same three layers from the demo.
    • Reads the README out loud.

    Predict“What do you think the README is for?” (It's the front page of the book: it tells visitors what the project is.)

  2. step 2 · 7 min

    Time travel through the history

    She clicks
    1. Click 2 commits (top right of the file list).
    2. Open f2f773b, then 344a553.
    She checks
    • Reads each sticky note (the commit message).
    • Explains the colours: green = added, red = removed.

    Predict“If we change just one word on one line, how many red and green lines will we see?” (One red: the old line. One green: the new line.)

  3. step 3 · 12 min

    Make a practice branch and change the heading

    She clicks
    1. Open index.html and click the pencil (Edit).
    2. Find <h1>Today's cakes</h1> and type her new heading.
    3. Click Commit changes…
    4. Choose Create a new branch, name it lizzie-new-heading, then Propose changes.
    She checks
    • Decides the new heading.
    • Writes the commit message: what changed, in a few words, like “Change heading to Lizzie's favourite cakes”.

    Predict“Will the live site change now?” Then refresh the live site to check. (No. The change is only on the practice branch.)

  4. step 4 · 8 min

    Open a pull request and check the change

    She clicks
    1. GitHub shows the pull request form. Click Create pull request.
    2. Open the Files changed tab.
    3. Wait about a minute for the Vercel bot comment. You open its Preview link on your laptop and show her.
    She checks
    • Checks the red and green lines match her prediction from step 2.
    • Looks at the preview and gives the verdict: “Is this what I wanted?”

    Predict“Why would a real team check a change before it goes in the real book?” (To catch mistakes before customers see them.)

  5. step 5 · 5 min

    Merge it, and watch the live site change

    She clicks
    1. Click Merge pull request, then Confirm merge.
    2. You show the new deployment appearing in your Vercel dashboard.
    She checks
    • Refreshes the live site on her own device every 30 seconds or so until her heading appears.

    Predict“How long until the live site changes: one second, one minute, or one hour?” (Usually under a minute.)

  6. step 6 · 5 min · if there's time

    Undo it (nothing is ever lost)

    She clicks
    1. On the merged pull request, click Revert.
    2. Create the new pull request and merge it.
    She checks
    • Watches the live site go back to Today's cakes.
    • Opens the history and finds that even the undo is a commit.

    Predict“After we undo it, is her heading gone forever?” (No. It's still in the history and can be brought back.)

If something goes wrong

The live site didn't change after 2 minutes

Check the Vercel dashboard. If there's no new deployment, the GitHub link isn't working: open the project's Settings → Git and connect sujjas/lilelus-html-css-js-demo. If there's a deployment marked Error, open it to read why. Meanwhile, use it as a teaching moment: “Real developers check the logs. Let's look.”

The Preview link asks for a Vercel login

That's Vercel's preview protection, so it's expected. Show the preview on your screen, or switch protection off under Settings → Deployment Protection.

The pencil (Edit) button is grey

She hasn't accepted the collaborator invite yet (check her email or github.com/notifications), or she's signed out.

She typed the heading but the page looks broken

A tag was probably deleted by accident, like the </h1>. Look at the red and green lines in Files changed: the mistake will be there. Fix it with another commit on the same branch. It's great debugging practice.

How to follow her work

any time

Everything she does in the repo is recorded by GitHub under her own name. She can see the same records you can, so nothing is hidden from her.

Explain back + journal

10 min

Lizzie's sheet

copy or print this part

GitHub words

repository (repo)
The magic recipe book: the whole project and all its files.
commit
Saving your changes, with a note saying what you changed.
commit message
That note. Keep it short and clear.
history
Every saved version, ever. Nothing gets lost.
diff
The red and green lines that show exactly what changed.
main
The real book. Vercel puts this one on the live site.
branch
A practice copy where you can try things safely.
pull request
Asking “can my change go into main?”
merge
Saying yes: the change joins main.
revert
Undoing a change, with a new commit.

Questions

  1. In your own words, what is a commit?
  2. Why did we make a branch instead of changing main straight away?
  3. What happened to the live site when we merged, and why?
  4. Write a good commit message for: “I changed the button colour to green.”
  5. Why should you never put a phone number or password in a public repo?
